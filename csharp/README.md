# Driving comio from C#

The second projection of the same metadata, and the reason it exists is not
coverage for its own sake: it is an independent reader. Where PyWinRT is
lenient, CsWinRT is strict, and the difference found a real defect in our
`.winmd` that Python had been quietly tolerating.

```text
ctor worked, transport = namedpipe
listening on \\.\pipe\comio_cs_19368
accepted via ConnectionReceived event
server read 'hello from c#'
CS-ROUND-TRIP-OK
```

## Running it

```bash
cargo build --lib --all-features        # the component
cargo test --all-features --test activation   # writes the reg-free manifest
dotnet run --project csharp/accept.csproj
```

Reg-free activation here is the simplest form there is: the
`<activatableClass>` entries ride on the exe's own application manifest
(`app.manifest`), so there is no registry read and no `CreateActCtx` call.
Python needs the run-time form only because `python.exe`'s manifest is not
ours to edit.

## What it proved

**A constructor exists.** `new NamedPipeConnector()` compiles and runs.
PyWinRT gives these same classes no `__new__`, so that is a PyWinRT
requirement — it wants a `.ctor` MethodDef row on the class, which MIDL
emits and `windows-rdl` does not — and not a deficiency in the metadata.
CsWinRT is satisfied by `ActivatableAttribute` alone. `python/` keeps its
workaround; the upstream report belongs with PyWinRT.

**A real event exists.** `listener.ConnectionReceived += handler` is a C#
event, not a pair of `add_`/`remove_` calls.

That second one did not work at first. CsWinRT refused the whole file:

```text
error: Type 'Windows.Foundation.TypedEventHandler' could not be found
```

`windows-metadata` 0.100 wrote an event's handler type as a plain
`TypeRef(namespace, name)`, discarding the generic arguments and the arity
suffix, so the Event row referenced `Windows.Foundation.TypedEventHandler` —
which does not exist, the real name being ``TypedEventHandler`2``. Our
`.winmd` contained both spellings: the correct one in the `add_`/`remove_`
signatures, the broken one in the Event row. Every WinRT event handler is
generic, so every event that version emitted was malformed. PyWinRT never
looked at the row — it infers events from `add_`/`remove_` naming — which is
exactly why a second consumer was worth building.

It is fixed on `windows-rs` master, which `tools/winmdgen` is now pinned to.
Across that upgrade all nine derived IIDs stayed identical and
`src/comio/bindings.rs` regenerated byte for byte unchanged, so only the
metadata moved — not the ABI.
